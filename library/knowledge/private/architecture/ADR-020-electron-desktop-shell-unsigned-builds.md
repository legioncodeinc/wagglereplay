# ADR-020: Studio's desktop shell is Electron; builds ship unsigned for now

Status: Accepted (2026-08-21). Fills in the framework choice ADR-016 left open; see Supersession and interaction.

## Context

ADR-016 committed Studio to a packaged desktop application that hosts the local Node runtime and the loopback server, but deliberately deferred the "Tauri or Electron" choice to the implementing PRD, and the desktop PRD (expected prd-018) cannot be authored against an open framework question. The deciding facts are already fixed elsewhere in the accepted ADR set: Studio is a Node application at its core — the loopback server, ffmpeg child pipelines (ADR-003), Playwright browser orchestration, and filesystem project access (ADR-015) all presume the Node runtime ADR-016 says the installed app must own — and ADR-017 requires provider-key encryption backed by each platform's OS secret store with a headless-Linux fallback. Separately, packaging introduces a signing question ADR-016's consequences named (code signing and notarization on macOS) but no decision yet records: a code-signing certificate is on hand, but the maintainer chooses not to run the signing ceremony for initial distribution, and users install past the OS warnings instead.

## Decision

The desktop shell is Electron. The Electron main process is Node, so it hosts the existing Studio loopback server directly — no sidecar runtime, no separate process lifecycle to manage — while the existing Svelte Studio UI ships as the renderer under contextIsolation, nodeIntegration disabled, a sandboxed renderer, and a content security policy; filesystem, ffmpeg, and Playwright work stays behind the main process, which retires the standing Vite `node:` builtins warnings by making the boundary explicit instead of normalizing it. Provider-key storage uses Electron's safeStorage, which is a direct implementation of ADR-017's Keychain/DPAPI/libsecret decision including the platform coverage it requires. The `waggle://` protocol registration and single-instance window focus implement ADR-016's launch path. The implementing PRD pins an Electron major and verifies its embedded Node satisfies the repository's Node 24+ engine floor before anything ships.

Builds ship unsigned and un-notarized for now. The existing certificate stays unused; users override Windows SmartScreen and macOS Gatekeeper to install. This is a packaging-pipeline posture, not an architectural commitment: enabling signing and notarization later is a build-configuration change, not a code change, and nothing in this decision constructs a dependency on staying unsigned.

## Consequences

No sidecar runtime management, and ADR-017's cross-platform crypto becomes the cheapest part of the desktop work, at the cost of an installer roughly 100 to 200 MB larger than a Tauri baseline, since Electron embeds Chromium and Node; that embedded runtime carries its own CVE surface and wants an update cadence, and its Node version must be re-verified against the engine floor at every Electron major bump. Shipping unsigned means every install trips a SmartScreen or Gatekeeper warning the user must knowingly dismiss, locked-down or managed machines may refuse the binary outright, and a practical auto-update channel is off the table while builds are unsigned — update prompts that themselves trigger the same warnings are worse than none, so the initial update path is simply downloading the next installer. Download and README copy must say plainly that the warning is expected, who the publisher is, and how to override it, or the distribution will read as malicious. The implementing PRD inherits explicit security obligations because packaging is distribution: the per-launch loopback authentication token that closes the standing Studio Low finding, plus the renderer hardening named above. Whether Playwright's Chromium and ffmpeg bundle as app resources or download on first run stays open for that PRD to decide.

## Alternatives Considered

Tauri, for its far smaller binaries and memory footprint. Rejected: the Studio server needs Node regardless, so Tauri forces a sidecar Node binary with its own lifecycle, version pinning, and IPC bridging — exactly the process-management burden ADR-016's single-installed-binary framing exists to avoid — and its keychain access needs extra wiring where Electron's safeStorage maps onto ADR-017 one-to-one. Sign and notarize from the first release using the certificate already on hand. Rejected for now: the ceremony, notably Apple's notarization round-trip, which is a separate gate from code signing itself, adds release friction with no functional gain for a personal tool whose users can override the warnings; the certificate remains available and the build pipeline can adopt it later without architectural change.

## Supersession and interaction

Does not supersede ADR-016; this record fills in the framework choice ADR-016 deliberately deferred, and defers activation of the signing and notarization surface ADR-016's consequences named. Enables ADR-017's implementation via safeStorage without revising it. Interacts with ADR-019: the desktop bundle adds no CLI surface, and packages/cli keeps its separate npm distribution for automation and the prd-012 CI path. The implementing desktop PRD inherits the hardening obligations stated above.
